Tinda

Point of sale and back office for Philippine retail

Private · walkthrough on request

Point of sale, books, inventory, purchasing and payroll for Philippine retail, in one system. The cashier rings sales, the Z-reading posts itself to the ledger, and every tax and payroll rule names the issuance it implements. Designed to the Philippine tax authority's (BIR's) technical requirements for accredited POS software; not yet accredited. Built over about three months.

Screens from a local demo run with a fictional store and seeded data. Click any image for full size.

  • Books can't be quietly edited. Journals are append-only and hash-chained, the database rejects UPDATE and DELETE, and a correction is a new adjustment document. This holds with real concurrent writers against real Postgres: a rollback leaves no gap in the numbering.
  • Every tax and payroll rule cites its source. VAT, senior/PWD discounts, SSS, PhilHealth, Pag-IBIG and withholding tax, plus the 1601-C, 2316 and Alphalist forms. Each rule names its issuance and effective date, and the agencies' own worked examples replay as test fixtures.
  • With an in-store server, the store keeps selling through an internet outage. Tills talk to an in-store server over the LAN, and invoice numbers stay gapless because they come from reclaimable blocks the server issues. A per-till mirror for cloud installs is built and tested; its desktop wiring is in progress. A retried sale or payment can't be recorded twice: the sale, payment, adjustment, AR/AP and reading endpoints take an idempotency key.
  • Runs the way the store needs it. An on-prem box, a cloud deployment, or a desktop register that drives USB receipt printers natively, all from one codebase. The business rules can't depend on the database: a CI test fails the build if the core imports it.

Distributor invoicing → SFA integration

Client work for a Philippine FMCG distributor (anonymized)

Client · private

An internal app the distributor's staff use to upload delivery invoices and returns to their sales-force-automation platform. In production since 2023; characterization-tested and hardened in 2026 so an invoice can't upload twice, go missing, or be marked uploaded when it wasn't.

  • An invoice can't be uploaded twice, or marked uploaded when it wasn't. Only owned, pending, unchanged rows go out. Each invoice number can have only one active invoice across all users (matched case-insensitively, with Postgres advisory locks). The upload lock is held across the remote call with bounded timeouts, and invoices can't be edited while an upload is in flight.
  • A release no longer means a 29-minute outage. A deploy script that had caused a 29-minute outage was replaced by a health-checked deploy with a rollback script. Its first measured cutovers (105 s and 44 s) had no downtime; that was later traded for a smaller instance.
  • Backups are proven restorable, not assumed. Nightly dumps go to S3 on systemd timers. A restore is verified with per-table row counts and an md5 over the sorted rows, and it refuses to run with stale helper scripts. The backup path has its own CI test.
  • Cheaper to run and harder to get into. Moved off managed Postgres and down two instance sizes, checking memory after each step. Access is SSM-only (no SSH), traffic comes in through a Cloudflare Tunnel, images are pushed with an OIDC push-only role, and CI actions are pinned to commit SHAs.

Trading bot

Supervised multi-strategy crypto trading

Private · walkthrough on request

Futures strategies run as fault-isolated modules in one supervised process against a live exchange account in USDT-margined perpetual markets: a higher-timeframe structure trader, per-symbol scalpers and a news monitor that can throttle or halt trading. Order entry is a committed mode switch, off as of October 2026, so the process reconciles positions and trades on its shadow (paper) ledger. A spot accumulation ladder runs alongside it as a separate app.

Winning trades from the bot's shadow (paper) ledger. These are simulated trades on live market data, not real-money fills. The list is filtered to wins. Results are shown in R, meaning multiples of the amount risked; amounts, position sizes and strategy names are masked.

  • A crash can't reset the daily loss limit. The circuit breaker, daily-loss cap and loss streak are rebuilt from the positions ledger on every restart. On boot, the bot flags any futures position its database can't explain.
  • Scalper strategies can run shadow-only first. A shadow ledger records their would-be trades and every rejected trade. Position size is always risk ÷ stop distance, the news monitor acts only on corroborated signals, and rate limits trigger backoff.
  • What you backtest is the code that runs. Backtests use the same logic and configs as production, were validated against recordings of the systems they replaced, and are checked against golden files.
  • A mistake that happened once can't happen again. A custom linter (~27 rules) runs before every test run, and each rule comes from a real incident. After one trader read another's positions, "unscoped position read" became a permanent rule.

Pipeline Pulse

Recruiting-pipeline analytics dashboard

Live demo ↗

A phone-friendly dashboard for a fictional recruiting agency, built as a demo for a client proposal: a manager opens it and sees this week's pipeline, conversion rates and cost-per figures, read straight from the team's Google Sheet. Every name, email and number is generated; log in with one click as a viewer or a master.

  • Duplicate and malformed leads don't inflate the funnel. People are deduped by normalized email, then phone, across tabs, and test leads are excluded. Date serials, ISO strings and mixed day/month formats are parsed, and the ones that can't be parsed are counted on a data-quality strip.
  • This week's numbers mean this week. Each stage counts in the Monday–Sunday Pacific week of its own date (a blank one falls back, visibly, to the lead's creation date), across both DST transitions. The suite runs under three time zones (Manila, UTC and London) so a time-zone bug can't hide behind the machine's clock.
  • Cost-per figures are exact to the cent. Ad spend is stored in integer cents, and cost-per figures use BigInt half-up division. A zero denominator shows "no data", not a number.
  • Viewers see only what they're allowed to. Viewer and master roles ride on signed JWT sessions; viewers see quiz results as pass/fail only. An import test parses the code and fails the suite when a layer reaches outward, and credentials stay in server-only modules.

Agentic Coding with Xcode

Two SwiftUI apps on Swift 6 packages

Public repo ↗

Two SwiftUI apps: MovieBrowser (search and browse TMDB) and SocialFeed (sign in, a feed that updates live, likes that show instantly, image posts). Built on Swift 6 packages so the app logic never depends on Firebase.

  • The app's logic never imports Firebase. The core package has no dependencies and cannot import Firebase. Dependencies are injected at a composition root, view models depend only on protocols, and there is one LoadState enum per app.
  • The feed updates live and a like shows instantly. The Firestore listener is wrapped in an AsyncThrowingStream. Optimistic likes are reconciled by the listener's echo, and the packages compile in Swift 6 language mode with no Combine.
  • Search waits for you to stop typing, and the test doesn't wait at all. Search debounce uses task cancellation with an injected Clock, so it is tested deterministically with a test clock.
  • UI tests run with no network and no secrets. A stub network mode means UI tests need no network and no token. CI runs swift test on the three dependency-free packages.

How I work

01

Fewer surprises after launch

Every change starts with a failing test, aimed at the places bugs hide: rounding, rollback, retries, tampering and two people doing the same thing at once. In the POS, mutation testing checks that the tests would actually catch a bug, so a green run means something.

02

New features don't break what works

If a rule matters, a machine enforces it: Tinda's build fails if the core imports the database, the trading bot's linter runs before the tests, and the iOS core can't import Firebase. Code that moves or decides money gets the hardest checks; everything else is checked lightly, on purpose.

03

A paper trail you can audit

Each of the three larger private projects keeps a numbered decision log, so the next developer knows why the code is the way it is. Where docs state a status, a CI check compares it against the code, so a stale guarded claim fails the build.

I run AI coding agents like a team, with gates I designed

A planner attacks the brief before any code exists, an implementer works test-first, and an independent adversary tries to break the change. Nothing merges when only its author has reviewed it. I own the architecture, the test strategy and the final review; the agents do the typing.
