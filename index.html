Tinda

Point of sale and back office for Philippine retail

Private · walkthrough on request

An offline-first POS, general ledger, inventory, purchasing and payroll in one codebase. It is designed to the Philippine tax authority's (BIR's) technical requirements for accredited POS software. It is not yet accredited. Built over about three months.

Screens from a local demo run with a fictional store and seeded data. Click any image for full size.

  • Tamper-evident books. Journals are append-only and hash-chained. Database triggers reject UPDATE and DELETE, and a correction is a new adjustment document. The chain's tail lock is tested with real concurrent writers against real Postgres: parallel writes, rollback without a numbering gap, and deadlock-free lock ordering.
  • Two pure statutory rules engines. One covers VAT, senior/PWD discounts and the Z-reading cross-check. The other covers SSS, PhilHealth, Pag-IBIG and withholding tax, plus the 1601-C, 2316 and Alphalist forms. Every rule cites its issuance and effective date, and the agencies' own worked examples replay as golden fixtures.
  • Offline-first by design. An in-store server with an optional mirror on each till. Invoice numbers are gapless and come from reclaimable blocks the server issues. The transmission outbox is written in the same transaction, and sale, payment, adjustment, AR/AP and reading endpoints take an idempotency key.
  • The architecture is enforced by tests. core → db = 0: a CI test fails the build if the core imports the database layer. The same codebase ships as an on-prem appliance, a cloud deployment and a Tauri desktop register that drives USB receipt printers natively.

Trading bot

Supervised multi-strategy crypto trading

Private · walkthrough on request

Several strategies run as fault-isolated modules in one supervised process, trading live capital in spot and USDT-margined perpetual markets: an accumulation ladder, a higher-timeframe structure trader, short-timeframe scalpers, and a news monitor that can throttle or halt trading.

Winning trades from the bot's shadow (paper) ledger. These are simulated trades on live market data, not real-money fills. The list is filtered to wins. Results are shown in R, meaning multiples of the amount risked; amounts, position sizes and strategy names are masked.

  • Safety gates that survive crashes. The circuit breaker, daily-loss cap and loss streak are rebuilt from the positions ledger on every restart, so a crash loop cannot reset them. Boot reconciliation flags futures positions the database can't explain.
  • A custom architecture linter (~27 rules) runs before every test run. Rules come from real incidents. For example, after one trader read another's positions, "unscoped position read" became a permanent rule.
  • Shadow-first rollout. Unproven strategies trade on paper first, and a shadow ledger records every rejected trade. Position size is always risk ÷ stop distance. The news monitor fails open and acts only on corroborated signals. Rate limits and ban responses trigger backoff.
  • Backtests run the live code. Backtests use the same logic and configs as production. They were validated against recordings of the systems they replaced and are checked against golden files.

Distributor invoicing → SFA integration

Client work for a Philippine FMCG distributor (anonymized)

Client · private

An internal invoicing app that uploads delivery invoices and returns to the distributor's sales-force-automation platform. It was built in 2023, then characterization-tested and hardened in 2026. The goal: no duplicate invoice numbers, no lost uploads, and no invoice falsely marked as uploaded.

  • Uploads are idempotent and safe under concurrency. Only owned, pending, unchanged rows go out. Each invoice number can have only one active invoice across all users (matched case-insensitively, with Postgres advisory locks). The upload lock is held across the remote call with bounded timeouts, and invoices can't be edited while an upload is in flight.
  • From outage to cutover. A deploy script that had caused a 29-minute outage was replaced by a health-checked deploy with a rollback script. Its first measured cutovers (105 s and 44 s) had no downtime; that was later traded for a smaller instance.
  • Backups you can trust. Nightly dumps go to S3 on systemd timers. A restore is verified with per-table row counts and an md5 over the sorted rows, and it refuses to run with stale helper scripts. The backup path has its own CI test.
  • Leaner and locked down. Moved off managed Postgres and down two instance sizes, checking memory after each step. Access is SSM-only (no SSH), traffic comes in through a Cloudflare Tunnel, images are pushed with an OIDC push-only role, and CI actions are pinned to commit SHAs.

Agentic Coding with Xcode

Two SwiftUI apps on Swift 6 packages

Public repo ↗

MovieBrowser is a TMDB client with a paginated list, debounced search and a detail screen. SocialFeed uses Firebase for auth, a real-time Firestore feed, optimistic likes and image posts. Both apps are built on local Swift packages, and the compiler enforces the Firebase boundary.

  • The compiler enforces the boundary. The core package has no dependencies and cannot import Firebase. Dependencies are injected at a composition root, view models depend only on protocols, and there is one LoadState enum per app.
  • Structured concurrency throughout. The Firestore listener is wrapped in an AsyncThrowingStream. Optimistic likes are reconciled by the listener's echo, and the packages compile in Swift 6 language mode with no Combine.
  • Deterministic time. Search debounce uses task cancellation with an injected Clock, so it is tested deterministically with a test clock.
  • Hermetic UI tests. A stub network mode means UI tests need no network and no token. CI runs swift test on the three dependency-free packages.

Working style & discipline

How I work

01

Test first, adversary second

Every change starts with a failing test, and I read the failure message before making it pass. Test suites target the places bugs hide: boundaries, rounding, rollback, idempotency, tamper detection and concurrency. Mutation testing checks the tests themselves. A green run doesn't count as evidence until I've seen that same check go red.

02

Machines enforce the boundaries

Tinda's CI fails if the core imports the database. The trading bot's ~27-rule linter runs before the tests. The iOS core package can't import Firebase. If a rule matters, a machine enforces it.

03

Decisions are written down

34 ADRs, ~170 numbered decisions and 44 decision records across the three private projects. Where docs state a status, a CI guard checks it against the code, so drift in guarded claims fails the build.

04

Depth by consequence

Code that moves money, decides an amount, or writes a record that an amount is later read from gets the hardest gates. Everything else is gated lightly, and I record that call, so a light gate is a decision rather than an oversight.

I run AI coding agents like a team, with gates I designed

A planner attacks the brief before any code exists. An implementer works test-first. An independent adversary tries to break the change. Nothing merges when only its author has reviewed it.

I own the architecture, the test strategy, the decision log and the final review. The agents do the typing, and I measure what each role costs.

  1. Plan the brief is attacked before code
  2. Red a failing test, with the right failure message
  3. Green the smallest change that passes
  4. Adversary an independent reviewer tries to break it
  5. Docs status is updated in the same change
